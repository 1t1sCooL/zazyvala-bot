# Базовые правила проекта

> Конвенции выведены из выбранного стека (NestJS + TypeScript + Prisma). Кодовой базы ещё нет — правила задают стартовый стандарт. Редактируйте по мере развития проекта.

## Конвенции именования

- Файлы: `kebab-case` с суффиксом роли — `summon.service.ts`, `bot.update.ts`, `chat-settings.dto.ts`, `members.module.ts`.
- Переменные и функции: `camelCase`.
- Классы, провайдеры, модули: `PascalCase` (`SummonService`, `MembersModule`).
- Константы и env-ключи: `UPPER_SNAKE_CASE`.
- Модели Prisma: `PascalCase` (`Chat`, `ChatMember`, `Assistant`).

## Структура модулей

- Модульная архитектура NestJS: один домен — один модуль (`bot`, `chats`, `members`, `summon`, `assistants`, `settings`, `admin`).
- Тонкие Telegram-хендлеры (`*.update.ts`) — только разбор апдейта и вызов сервиса; бизнес-логика в `*.service.ts`.
- Доступ к БД — через Prisma-сервис/репозитории, доменные сервисы не работают с SQL напрямую.
- DTO и валидация входных данных — через `class-validator` / `class-transformer`.

## Обработка ошибок

- Доменные ошибки — через исключения NestJS (`BadRequestException` и т.п.) или собственные классы ошибок.
- Ошибки Telegram API (429 / Flood control) — ретраи с экспоненциальным backoff; частичный сбой зова не должен ронять процесс.
- Никаких «проглоченных» ошибок — логировать с контекстом.

## Логирование

- Встроенный `Logger` NestJS (или `nestjs-pino` при необходимости структурированных логов).
- Уровень логирования управляется через `LOG_LEVEL`.
- Не логировать секреты (токен бота, `DATABASE_URL`).

## Тестирование

- Jest (поставляется с NestJS): unit-тесты сервисов (`*.spec.ts`), e2e для критичных сценариев (`test/*.e2e-spec.ts`).
- Логику зова и батчинга покрывать unit-тестами как ядро продукта.
