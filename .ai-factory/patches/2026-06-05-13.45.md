# Под падал на старте: изменённая миграция 0001_init ломала migrate deploy

**Date:** 2026-06-05 13:45
**Files:** Dockerfile, package.json, prisma/migrations (удалена), README, AGENTS
**Severity:** critical

## Problem

После деплоя свежего образа бот перестал отвечать вообще (даже на /help). Под
в CrashLoopBackOff — приложение не стартовало.

## Root Cause

При добавлении полей (`lastSummonAt`, `callPolicy`, `blacklisted`) я каждый раз
**перегенерировал один и тот же файл миграции** `prisma/migrations/0001_init/
migration.sql` через `migrate diff --from-empty`, вместо создания новых миграций
(0002, 0003...). В БД уже был применён старый `0001_init`. Контейнер на старте
выполнял `prisma migrate deploy`, который обнаруживал, что **уже применённая
миграция изменена** (несовпадение checksum) и падал с ошибкой → `&& node
dist/main` не выполнялся → под крашился → бот офлайн.

## Solution

На этапе активной разработки схемы перешёл на `prisma db push` — идемпотентную
синхронизацию схемы с БД без истории миграций и без ловушки с checksum:

- Dockerfile CMD: `npx prisma db push --skip-generate --accept-data-loss && node dist/main`.
- Удалил мутировавшую папку `prisma/migrations/`.
- npm-скрипт `db:migrate*` → `db:push`. README/AGENTS обновлены.

Когда схема стабилизируется — вернёмся к полноценным миграциям (`migrate`),
создавая НОВЫЙ файл на каждое изменение, не трогая применённые.

## Prevention

- НИКОГДА не редактировать уже применённую миграцию — только новый файл.
- На этапе прототипа использовать `prisma db push`; миграции — когда схема устаканится.
- Проверять контейнер не только сборкой, но и запуском (под/логи) — краш на
  старте сборкой не ловится.
